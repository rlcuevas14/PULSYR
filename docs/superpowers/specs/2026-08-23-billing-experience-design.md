# Billing experience (Paddle) — design spec

**Date:** 2026-08-23
**Status:** Approved design (pending spec review) → next: writing-plans
**Author:** Rodolfo + Claude
**Scope:** Let a hosted account buy, change and cancel a paid plan: a pricing hand-off from the public site, and a billing screen inside the app that shows the current plan, usage against its limits, and the upgrades and downgrades available.

---

## 1. Problem and current state

Paddle is wired as far as the money coming *in*. Nothing lets a customer start, change or stop paying.

| Fact | Evidence |
|---|---|
| The sandbox catalog exists: two products, four prices, each price stamped with `custom_data.plan_code`. | Paddle sandbox, created 2026-08-23 |
| `POST /webhooks/paddle` verifies the signature and mirrors subscription state onto `account_subscriptions`. | `app/webhooks/router.py`, `app/webhooks/service.py` |
| Entitlements are enforced server-side for four resources. `PAID_LIMITS` already carries the Solo and Studio numbers. | `app/accounts/plans.py` |
| `v0026` added `paddle_customer_id`, `paddle_subscription_id`, `paddle_event_at` and widened the plan check to `solo` and `studio`. | `migrations/versions/v0026_paddle_subscriptions.py` |
| **No way to buy.** No checkout, no plan change, no cancellation, no billing screen. An account can only reach a paid plan by someone hand-writing a row. | grep: no `PADDLE_API_KEY`, no `/billing` route |
| The public site prices link nowhere: the pricing section says "not open for signup yet". | `pulsyr-landing/i18n/en.json` |

## 2. Goals and non-goals

**Goals**

- A logged-in owner can move between Free, Solo and Studio, monthly or yearly, and cancel, without leaving Pulsyr except to type card details.
- The billing screen states the truth about what the account is paying and how close it is to its limits, using the same counts the entitlement guards use.
- One source of truth for plan state: the webhook. The UI never decides a plan.
- The public site keeps its no-executable-JavaScript posture.
- A self-hosted instance never sees any of it.

**Non-goals**

- Invoices generated by Pulsyr. Paddle MSA clause 10.1 forbids invoicing a Paddle transaction.
- Per-seat quantity billing. Catalog prices are locked to quantity 1.
- Coupons, discounts, trials, dunning emails. Paddle Retain handles retries; Free is the trial.
- Metering AI operations. The Terms publish a monthly AI limit, but no counter exists yet and this spec does not add one.

## 3. Decisions

| Decision | Choice | Why |
|---|---|---|
| Where a purchase starts | **Signup first.** Public-site price buttons link to `/signup?plan=…&cycle=…`; checkout always happens with a session. | One purchase path, `account_id` always known at checkout, no orphan payments to reconcile. |
| Over-quota after a downgrade | **Freeze, never delete.** Existing data stays readable and writable; only creating new resources is blocked until the account is back under its limit. | Exactly what `ensure_*_capacity` already does, so it is zero new code, and it honours the Terms promise never to delete data over a quota. |
| Who executes a plan change | **The app, through the Paddle API.** The Paddle customer portal is used only for payment method and invoices. | Matches the classic billing-screen UX; keeps retention copy and error handling ours. |
| Upgrade money | `prorated_immediately` with `on_payment_failure: prevent_change`. | The customer gets capacity now and pays the difference now; if the card declines, no plan is granted. |
| Downgrade money | `prorated_next_billing_period`. | Paddle's update endpoint always switches the plan immediately; only the billing timing is selectable. This credits the difference at renewal instead of issuing a mid-period refund. |
| Cancellation timing | `effective_from: next_billing_period`. | The Terms say access continues until the end of the paid period. |

### 3.1 Correction carried into this design

An earlier reading assumed a downgrade could be made effective at the end of the paid period. It cannot: `subscriptions.update` applies the item change immediately in every proration mode. **A downgrade therefore reduces capacity immediately**, with the money adjusted at renewal. The freeze-never-delete rule is what makes that acceptable: an account that drops from Studio to Solo with 12 projects keeps all 12, and simply cannot create the 13th.

The billing screen must say this before the user confirms, not after.

## 4. Architecture

### 4.1 Module layout

New module `app/billing/`, following the module-per-domain convention:

| File | Responsibility |
|---|---|
| `paddle.py` | Outbound Paddle API client on `httpx`. Four calls: `get_subscription`, `preview_update`, `update_subscription`, `cancel_subscription`, plus `portal_session`. Degrades with no API key exactly like `app/ai/llm.py`: the module imports, the calls raise a typed error, the screen hides its buttons. |
| `router.py` | `GET /billing` (screen) and the `/ui/billing/*` HTMX action endpoints. |

The inbound webhook stays in `app/webhooks/`. `app/accounts/plans.py` stays free of any outbound HTTP: it is the entitlement authority and must remain easy to audit.

### 4.2 Two flows, not one

| Situation | Mechanism | Where it runs |
|---|---|---|
| Free → Solo/Studio | **Checkout** (Paddle.js overlay) with `customData: {account_id}` | Browser |
| Solo ↔ Studio, monthly ↔ yearly | `PATCH /subscriptions/{id}` | Server |
| Cancel | `POST /subscriptions/{id}/cancel` | Server |

The first case has no subscription to update, so it must open a checkout. This is why the integration needs two credentials rather than one: a client-side token for Paddle.js and a server-side API key.

Paddle.js loads only in the private app, which already uses CDN scripts for HTMX and Tailwind. The public site stays script-free.

### 4.3 State: what is mirrored and what is fetched

The two are deliberately split, because mirroring everything is what makes billing screens lie.

- **Mirrored** in `account_subscriptions`, written only by the webhook: `plan_code`, `status`, the Paddle ids, `paddle_event_at`. This is the hot path, read on every request that touches a limit.
- **Fetched live** from the Paddle API when `/billing` renders: next billing date, the scheduled change (a pending cancellation or downgrade), the current price and term, and the payment method on file.

The consequence is that no migration is needed for `scheduled_change`, and a pending cancellation can never go stale in our database. The cost is one outbound call on one low-traffic, owner-only page. If Paddle is unreachable, the screen still renders plan and usage from the mirror, and shows an inline notice in place of the billing detail.

### 4.4 The write path and its lag

Every change follows the same shape:

1. The browser posts to `/ui/billing/change`.
2. The router re-checks ownership, then calls Paddle.
3. Paddle confirms.
4. **The app writes nothing about the plan.**
5. The webhook arrives, typically under a second, and `apply_paddle_subscription` writes it.

The race is real: an owner who lands back on `/billing` before the webhook arrives would see the old plan. The screen therefore shows a `flash_success` reading "change submitted, it appears in a few seconds" rather than optimistically painting the new plan and contradicting itself if the webhook says otherwise.

### 4.5 The screen

`GET /billing`, owner-only, hidden entirely when the plan is `self_hosted`.

1. **Current plan**: name, price, term, next billing date, and any scheduled change stated in words ("Studio until 12 May, then Solo").
2. **Usage against limits**: projects, collaborators and deliverable storage as used-over-limit with a bar. The counts come from the same queries as the guards in `plans.py`, so the screen cannot drift from what the server actually enforces. Tokens per project are not shown: paid plans do not cap them.
3. **Plan cards**, one per available plan, each with the correct action: upgrade, downgrade, switch term, or cancel. The current plan is marked and has no button.
4. **A confirmation step** for any paid-to-paid change, showing Paddle's `preview_update` numbers verbatim ("you will be charged USD 12.40 today, then USD 20.00 monthly from 12 May"). The prorated amount is never computed locally: the preview accounts for tax, currency and credit balances we do not track.
5. **A `past_due` banner** when the mirrored status says so: the payment failed, Paddle is retrying, access continues, update the card.
6. **Payment method and invoices**: a link that mints a Paddle portal session and redirects.

### 4.6 Public site hand-off

Price buttons link to `/signup?plan=solo&cycle=monthly`. The app validates the pair against the known plans, keeps it in the session across the OAuth round trip, and opens that price's checkout as soon as the account exists. An unknown or missing pair degrades to the normal signup with no checkout.

The published Terms and the pricing section lose their "not yet in force" and "not open for signup yet" notices as part of the rollout, not before.

## 5. Config surface

| Setting | Purpose | Absent |
|---|---|---|
| `PADDLE_API_KEY` | Server-side subscription changes and portal sessions | `/billing` shows plan and usage, hides every action |
| `PADDLE_CLIENT_TOKEN` | Paddle.js overlay checkout | No upgrade from Free |
| `PADDLE_WEBHOOK_SECRET` | Already shipped in `v0026` work | Webhook answers 503 |
| `PADDLE_ENVIRONMENT` | `sandbox` or `production`, selects the API host and the Paddle.js environment | Defaults to `sandbox` |
| `PADDLE_PRICE_*` | **Not needed.** Prices are discovered from the Paddle API and mapped by `custom_data.plan_code`. | — |

## 6. Permissions

`require_owner` gates every billing route. A `member`, even one with editor grants on every project, gets 403: billing belongs to the account holder. The super-admin does not get access either, matching the existing rule that an instance operator manages accounts but not their data.

## 7. Errors and degradation

| Case | Behaviour |
|---|---|
| Paddle API unreachable while rendering | Plan and usage render from the mirror; billing detail replaced by an inline notice |
| Paddle API error on a change | The action returns a visible error, nothing is written locally, the plan is unchanged |
| Prorated upgrade charge declines | `on_payment_failure: prevent_change` means Paddle applies nothing; the screen reports the decline and points at the portal |
| Webhook never arrives after a successful change | The mirror stays on the old plan, which under-grants rather than over-grants. Recovery is the dashboard's notification log replay. |
| No API key configured | Actions hidden, screen read-only |

## 8. Security

- Every billing route re-checks ownership server-side; no action trusts a form field for the account.
- The subscription id acted upon is read from `account_subscriptions` for the owner's account, never from the request, so an owner cannot cancel another tenant's subscription by guessing an id.
- `PADDLE_API_KEY` never reaches a template. `PADDLE_CLIENT_TOKEN` is public by design and does reach the browser.
- Checkout `customData` carries only `account_id`. No email, no name, no project content.
- The existing webhook rate limit covers the inbound side; the outbound side is owner-only and unattractive to abuse.

## 9. Test matrix (CI is the gate)

| Area | Cases |
|---|---|
| Access | Owner reaches `/billing`; member gets 403; `self_hosted` plan hides the section |
| Rendering | Usage numbers equal the guard queries; `past_due` renders the banner; Paddle unreachable still renders plan and usage |
| Upgrade | Free → Solo opens a checkout with `account_id` in `customData` |
| Change | Solo → Studio calls update with `prorated_immediately` and `prevent_change`; Studio → Solo uses `prorated_next_billing_period` |
| Preview | The confirmation screen shows the preview values and never a locally computed amount |
| Cancel | Calls cancel with `next_billing_period`; the screen reports a scheduled cancellation, not an immediate one |
| Lag | A successful change with no webhook yet shows "submitted", not the new plan |
| Degradation | No API key: actions hidden, no 500 anywhere |
| i18n | Every new string exists in `en`, `es` and `fr` (enforced by `tests/test_i18n.py`) |

The Paddle client is mocked the way `app/ai/llm.py` is mocked. No test talks to Paddle.

## 10. Rollout

1. Ship with `PADDLE_ENVIRONMENT=sandbox` and no live keys. Nothing is buyable.
2. Verify end to end in sandbox with test cards and the webhook simulator: buy, upgrade, switch term, downgrade, cancel, and let a scheduled cancellation land.
3. Await Paddle live approval, create the live catalog with the same `custom_data`, swap the four environment values.
4. Remove the draft notices from the Terms, Refund Policy and Privacy Notice, and the "not open for signup yet" line from the public pricing section.
5. Open registration with the existing `VM env sync` workflow (`docs/operations/free-plan-launch.md`).

## 11. Open items

- **AI operation metering.** The Terms publish monthly AI limits per plan and nothing counts them. Out of scope here, but it is a published promise currently unenforced, and it should get its own spec.
- **Studio fair use.** `PAID_LIMITS` leaves Studio projects unmetered; the Terms name 25 as the point where we contact the customer. That contact is manual today.
- **Live tax categories.** `saas` is enabled in sandbox. Confirm it is enabled on the live account before the catalog is recreated.
